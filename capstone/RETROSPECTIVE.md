## Reflection

At the beginning of this work, I wanted a portfolio that could make my experience in AI evaluation, scientific reasoning and education easier to understand. A list of skills was not enough. I needed a place where someone could see a problem, understand my contribution and inspect the evidence behind the result. The project became a public portfolio, a small research-agent implementation, and a record of decisions and revisions. Its most useful outcome is a clearer way to show what has been demonstrated and what still needs validation.

One change came from peer feedback. Ruben said the projects did not clearly explain their achievements: what problem existed, what I did, and what happened afterward. That exposed a weakness in how I presented the work. The project cards were reorganized around problem, contribution and supported result, with links to evidence. The lesson goes beyond wording. If a reviewer has to reconstruct the value of a project, I have left too much work for them. A clear explanation is part of the deliverable.

My technical choices also became more concrete. The portfolio kept plain HTML, CSS and GitHub Pages because the main requirement was to publish inspectable evidence. Later, a small JavaScript feature added live GitHub reads. It retrieves a repository snapshot and links the selected project's files to that commit. This gives a reviewer a specific version to inspect. It does not prove those files are correct. That distinction helped me understand the difference between retrieving data, presenting evidence and making a justified claim.

The Research Scout involved another decision. Its specification proposed a ChatGPT-based surface, while the implementation moved to Python and Gemini with Google Search grounding. The reason was reproducibility and a visible request-to-output path. The build log preserves that change instead of pretending the plan never changed. The source and evaluation cases are available, but a successful live model run is not recorded in the package yet. I would rather identify that gap than describe an implementation as validated because it looks complete.

Testing changed how I think about finished work. Browser checks, simulated API failures and physical-phone observations answer different questions. A fixture can show that an error message appears when a request fails; it cannot prove the public service responded successfully. My Samsung A15 observations add a real device check, while the published hardening record documents the automated scenarios. The analytics screenshot adds another narrow observation: Cloudflare recorded three visits and three page views in its displayed period. It does not prove three different people visited or that the traffic was organic.

The first transferable skill I take from this is evidence-based judgment. I can separate a requirement, an implementation, an observation and a conclusion, then ask whether the conclusion actually follows. The second is scope control. A read-only integration and a small agent are easier to understand than a larger system whose behavior I cannot explain. The third is communicating technical work to another person. README instructions, case studies and explicit limitations make the work more useful than code alone.

AI assistance accelerated planning, implementation, documentation and debugging throughout this project. That makes transparency necessary. I need to understand the decisions, inspect the output and correct claims that exceed the evidence. My next steps are to record the real agent demonstration, evaluate its source handling on the defined cases, and use those observations to decide what to improve. Before final submission, I also need to confirm the portal hours, publish through the program's required route, and complete the final review. The goal is a body of work I can explain, maintain and improve with evidence.
