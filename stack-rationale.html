Three Roads: Choose Your Stack with AI

A practical stack decision for an AI evaluation portfolio: three genuine options, the trade-offs behind each, and why the simplest one is the right choice for the work I need to show today.

Eduardo Seixas AI Evaluation Portfolio Chosen stack: GitHub Pages + HTML/CSS Backend: not yet

1. Constraints

Free only. I do not want the portfolio to depend on a paid hosting plan while I am still building and refining it.

Honest skill level. I am comfortable working with basic HTML, CSS, GitHub, and a simple static-site structure. I do not want the portfolio to become a framework-learning project. The purpose is to showcase AI evaluation work, not to prove that I can maintain a complex web application.

What the portfolio must display. The site needs to present case studies, screenshots, evaluation artifacts, PDFs, repository links, structured findings, and concise explanatory text. The design should stay quiet enough that evidence remains the focus.

Dynamic needs. Nothing currently needs to be dynamic. I do not need authentication, a database, server-side processing, or user-generated content at this stage.

2. Three Stack Options

Option 1 · Front-runner

GitHub Pages + plain HTML/CSS

How I would build it: keep the portfolio in a public GitHub repository, write the interface in standard HTML/CSS, and deploy it with GitHub Pages and GitHub Actions.

Where it would host: GitHub Pages, free.

Backend: none.

Real trade-off: if I later need authentication, databases, server-side logic, or advanced application behavior, GitHub Pages alone will not provide them. Today, none of those features are required.

Option 2

Netlify + static site

How I would build it: the same basic static site, connected to the GitHub repository and deployed through Netlify.

Where it would host: Netlify free tier.

Backend: not required, although the platform offers additional services if the project grows.

Real trade-off: Netlify adds useful deployment features, but for my current portfolio most of them would go unused. It would also introduce another platform to maintain without solving a problem I actually have.

Option 3

Vercel + a modern web framework

How I would build it: use a framework such as Next.js and deploy it on Vercel.

Where it would host: Vercel free tier for this scale.

Backend: optional; APIs and server-side behavior could be added later.

Real trade-off: this is the most powerful option, but it solves problems I do not currently have. A framework would add dependencies, configuration, build concepts, and maintenance overhead without making the evidence in my case studies stronger.

3. Pressure Test

The front-runner is GitHub Pages with plain HTML/CSS.

What breaks if I choose the simplest option? Future application-like features would require a different architecture or an additional service. GitHub Pages cannot become a full backend by itself.

Does that stop me from showing my work properly? No. My portfolio is based on screenshots, rubrics, findings, evaluation artifacts, written case studies, PDFs, links, and conclusions. All of these work well on a static site.

What do I maintain if I choose the most powerful option? A framework, package dependencies, build configuration, deployment conventions, and more moving parts. I can learn those things, but right now they would take attention away from improving the portfolio itself.

Can I finish the simple version quickly? Yes. In fact, the public GitHub Pages deployment is already live, which turns this choice from a hypothetical architecture into a working one.

4. Decision

I chose GitHub Pages with plain HTML/CSS.

I did not choose it because it is the most powerful stack. I chose it because it is the smallest stack that fully satisfies the real requirements of my portfolio.

I considered Netlify, which offers a similarly simple static deployment with more platform features, and Vercel with a modern framework, which offers much more room for dynamic development. Both are valid choices, but neither currently solves an important problem that GitHub Pages cannot solve.

The deciding factor is maintainability. A static site is small, transparent, version-controlled, and easy for me to inspect directly. If the portfolio later develops a genuine need for dynamic functionality, I can migrate then. I do not need to pay that complexity cost before the requirement exists.

Can I maintain this?Yes. The stack is small, understandable, version-controlled, and already working.
Does it show my work well?Yes. It keeps the technology quiet so the evidence, case studies, criteria, and conclusions remain the focus.

Backend: not yet. At this stage, adding one would increase complexity without improving what the portfolio is intended to demonstrate.
