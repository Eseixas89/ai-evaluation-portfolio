Como o DNS
encontra um site.

Antes de estudar esse assunto, eu associava DNS à mensagem de erro que aparece quando o navegador não consegue encontrar um site. Agora entendo que ele faz parte do caminho necessário para chegar até esse site.

Para mim, uma boa comparação é uma agenda de contatos. Eu lembro o nome de uma pessoa, mas preciso do número dela para telefonar. Na internet, acontece algo parecido: escrevemos o nome do site, enquanto o computador precisa de um endereço IP para se conectar ao servidor. O DNS, ou Sistema de Nomes de Domínio, ajuda a encontrar essa informação.

Quando alguém digita um endereço no navegador, a resposta pode já estar guardada temporariamente em cache. Se não estiver, o computador consulta um resolver, um serviço que procura a informação. Quando necessário, esse resolver consulta a hierarquia do DNS: os servidores raiz indicam onde procurar informações sobre a extensão do domínio, como .com; os servidores dessa extensão indicam os nameservers responsáveis pelo domínio.

O nameserver autoritativo fornece os registros daquele domínio. Registros A e AAAA informam endereços IP. Já um registro CNAME funciona como um apelido: ele aponta um nome para outro nome, que também precisa ser resolvido. Por exemplo, um endereço como www.exemplo.com poderia apontar para outro hostname. Isso não é a mesma coisa que redirecionar o visitante para outra página.

No meu portfólio, o DNS ajuda a localizar o servidor correspondente a eseixas89.github.io. A parte /ai-evaluation-portfolio/ é o caminho que o servidor usa para identificar meu projeto; ela não é resolvida pelo DNS.

Depois de encontrar o endereço, o navegador estabelece uma conexão HTTPS, verifica o certificado do servidor e solicita os arquivos da página. Assim, entendi que DNS e HTTPS têm funções diferentes: o DNS ajuda a localizar o serviço, enquanto o HTTPS protege a comunicação com ele. Um erro de DNS pode impedir que o navegador encontre o servidor, mesmo que os arquivos do site estejam funcionando.
